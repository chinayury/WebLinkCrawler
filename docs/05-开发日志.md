## 一、引擎健壮性与请求策略（Q-01 ~ Q-11）

> 本节为同类项目借鉴点落地过程中发现并闭环的问题，覆盖请求节奏、体检分级、解析分层、连接兼容、去重口径。

### Q-01 对不实现 HEAD 的站点，check_links 只发 HEAD，405/501 全判「异常」

- **现象**：对不实现 HEAD 的站点，`check_links` 只发 HEAD，405/501 全落入兜底 `error`，整站链接被判异常。
- **根因**：worker 只有 HEAD 一条路径，没有任何 GET 回退。
- **解决方案**：HEAD 取到回退集状态码（默认 `{405,501}`，403 opt-in）时，对同一 link 再发一次只读 GET（`read_body=False`，不读 body、不新增线程、节流复用 `_request`）并用 GET code 重新分级；GET 自身网络异常时回落原 HEAD 判定。落点：`crawler.py` worker / `_head_fallback_codes` / `config.py` `link_check` 默认值。

### Q-02 回退 GET 会退化成一次轻量全站抓取

- **现象**：若直接复用现有 GET 分支，405 站点会触发读 body 至 `max_html`（默认 5MB），一次回退变成一次轻量全站抓取。
- **根因**：`_perform` 的 GET 分支无条件 `_read_body`。
- **解决方案**：`_perform` 增加 `read_body` 参数，HEAD 与只读 GET 都只取状态/响应头后关闭响应体；测试用 mock 断言 `_read_body` 未被调用。

### Q-03 999 被判 error、304 被判 redirect

- **现象**：`_classify_status` 把 999 判 error、把 304 判 redirect（304 无 Location，并非重定向）。
- **根因**：判定集合硬编码 2xx/3xx 区间，无法按目标站点调整。
- **解决方案**：新增 `link_check.ok_status_codes`（默认 `[200,206,999]`），`_classify_status` 改为实例方法：2xx 基线 → 配置 OK 集（必须早于 3xx）→ 3xx → blocked → dead → error；仍只产 5 个 state key，展示/导出层零改动。

### Q-04 JSON/二进制 body 被当页面抽链

- **现象**：`_crawl_round` worker fetch 后直接 `extract_links`，对 `application/json`、`image/*`、二进制 body 也跑 BeautifulSoup，产生无用 CPU 与潜在伪链接。
- **根因**：抓取阶段缺少 Content-Type 检查。
- **解决方案**：插入 `_should_parse_body` 闸门（默认 `text/html` / `application/xhtml+xml` / `text/plain`，未声明类型按旧行为放行），只决定「要不要解析子链接」；明确与 `_passes_file_filters` 分层——闸门看本次响应头、零额外网络且绝不做大小/时限，文件过滤另发 HEAD 看 Content-Length/Last-Modified。

### Q-05 全局节流拖慢多站点体检

- **现象**：`_throttle_last` 是单个 float，快站点被慢站点槽位挤后。
- **根因**：节流簿记是全局标量，不区分主机。
- **解决方案**：换成 `_throttle_next: dict[str,float]`，键取 `urlsplit(url).netloc`（与 robots root 同口径）；`random.uniform(interval, interval*2)` 均匀抖动后写回 due；等待仍在锁外 ≤0.25s 切片保证 stop 唤醒；簿记超 4096 时丢弃最旧一半（2048 条，容量保护）。

### Q-06 robots.txt 并发重复抓取

- **现象**：`_robots` 只在读/写持锁，抓取在锁外，同站 8 个 URL 并发会打 8 次 robots.txt。
- **根因**：缺少 in-flight 去重。
- **解决方案**：新增 `_robots_inflight` 锁表 + `_root_lock(root)`，流程为查缓存 → root 锁 → 锁内二次查缓存 → 才抓取 → 写缓存；`_robots_cache` 保持普通 dict 并加 256 FIFO 上限，不引 LFU。关键约束：不能把 `_robots_lock` 放宽罩住抓取——同一路径两次 acquire 会自死锁（有源码级回归用例钉住）。

### Q-07 重构 `_robots` 破坏源码级回归测试

- **现象**：把抓取主体抽成 `_fetch_robots` 后，源码检查测试对 `_robots` 方法体断言失败。
- **根因**：源码检查绑定在 `_robots` 方法体上，抽取 helper 后符号迁移。
- **解决方案**：回退该重构，抓取主体保持内联在 `_robots` 内（仅外层加 root 锁与缓存容量控制），既得 in-flight 去重又不破坏外部测试。

### Q-08 429 错误页污染结果

- **现象**：429 响应被原样返回，worker 对错误页抽链，把限流页里的整站布局链接当成页面链接收进来。
- **根因**：全模块无 Retry-After 能力。
- **解决方案**：新增 `_parse_retry_after` / `_retry_wait` / `_fetch_with_retry`，429/503/408 先按 Retry-After 或指数退避重试（统一受 `retry_after_cap` 封顶，默认 30），次数用尽按失败处理（记 `[放弃重试]` 日志，调用方记 `[请求失败]` 日志并返回空链），不抽链、不产生任何体检记录。

### Q-09 停止指令被长退避阻塞

- **现象**：`_perform` 重试退避用 `time.sleep(delay)`（最长 30s），Crawl-delay 用 `time.sleep(min(delay,10))`，用户点停止后线程仍要睡满。
- **根因**：阻塞式睡眠不监听停止事件。
- **解决方案**：两处都换成 `self._stop_event.wait(delay)`，语义不变但可被 stop 即时唤醒；测试用「首次失败即置停止位」验证耗时 <1s。

### Q-10 同一 URL 被存 5 遍

- **现象**：每页都有 `#content` 等 fragment，以及 `utm_source` / `sid` 等噪声参数变体，同一 URL 被当成不同页面反复入库。
- **根因**：`normalize_url` 未处理 query 变体，且去重键直接用了原始 URL。
- **解决方案**：`config.py` 新增纯函数 `canonical_key`（query 排序 → 去空值 → 删黑名单名（白名单优先）→ 去重复键），`_normalize_links` 与 `crawl()` 改用「raw URL + canonical key」双轨制——导出/展示/入库一律写原始 URL，归一化结果仅作去重键。

### Q-11 老服务器 SSL 握手被拒

- **现象**：1024 位 RSA / 弱 DH 老站在 OpenSSL 3 默认安全级别下直接握手失败（EE certificate key too weak）。
- **根因**：默认上下文 SECLEVEL=2。
- **解决方案**：新增 `_SSLAdapter` 降 SECLEVEL=1（LibreSSL 抛 SSLError 时回退 DEFAULT），按 `network_policy.ssl_compat_legacy_servers` 开关（默认 False）挂载；必须同时覆写 `proxy_manager_for`，否则按请求传 proxies 的用户兼容能力会静默失效；证书链/主机名校验与 TLS 下限保持不动。

## 二、视觉重构 · theme.py / icons.py（V-01 ~ V-06）

### V-01 图标整体不显示（既有缺陷，本轮修复）

- **现象**：用新 `icons.py` 渲染图标接触表，35 个图标全部只剩背景色、无一出墨；回溯旧版代码，按钮/导航/面板图标同样缺失。
- **根因**：`tk.PhotoImage.put()` 要求「行列表」结构。旧实现传的是扁平颜色列表，Tcl 把每个颜色当成独立一行（整行纯色），于是每行只写入第一个颜色、区域又只有 1 行高，最终整图只剩首行首色。
- **解决方案**：`icons.py` `photo()` 改为 `img.put("{" + " ".join(cols) + "}", to=(0, py, size, py + 1))`；并新增回归断言 `test_icon_actually_draws_ink`（渲染 `search` 图标，要求前景像素 > 40），防止再次回退。

### V-02 浅色纸底导航下激活项文字不可见

- **现象**：新体系导航改为浅色纸底后，当前激活导航项文字仍为白色，白字浅底不可见。
- **根因**：激活态文字色写死 `fg="#FFFFFF"`（沿袭深色导航栏时代假设）。
- **解决方案**：改为 `fg=theme.RAIL_ACTIVE_FG if active else theme.RAIL_FG`；`theme.py` 新增 `RAIL_ACTIVE_FG` 令牌（默认墨 `#22262B`，两套旧配色覆盖为 `#FFFFFF`）。仅此 1 行改动，不动布局。

### V-03 聚焦边框按建议色取值会不可见

- **现象**：建议稿给「边框 `#E2DCCF` / `#EDE8DE`」；若把更浅的 `#EDE8DE` 用作 `BORDER_STRONG`（聚焦态），纸底上聚焦环几乎看不见。
- **根因**：`BORDER_STRONG` 的语义是「聚焦/强边框」，必须深于常规边框才构成可见的聚焦反馈。
- **解决方案**：`BORDER_STRONG` 下调一档取 `#C9C0AC`，`#EDE8DE` 改作 `DIVIDER`（面板内细分隔线）。这是本轮对建议色板的唯一调整。

### V-04 切到旧配色方案时导航文字会变成深色（不可见）

- **现象**：`PALETTES` 保留「黛蓝·琥珀 / 陶红·亚麻」两套深色导航方案；新基线 `RAIL_FG` 为深墨色，切换后深色导航栏上出现深色文字。
- **根因**：旧覆盖字典只覆盖 `RAIL/RAIL_ACTIVE/RAIL_LINE`，隐含假设基线 `RAIL_FG` 是浅色；新体系把基线反转为浅色导航，假设失效。
- **解决方案**：两套旧方案的覆盖项补齐 `RAIL_FG` / `RAIL_FG_DIM` / `RAIL_ACTIVE_FG` / `RAIL_HOVER` / `RAIL_EDGE` / `DISABLED_BG` / `DISABLED_FG` / `DIVIDER` / `PANEL_BAND_BG` / `PANEL_BAND_LINE` / `STRIPE` / `TREE_HEAD_BG`；新增配色机制测试断言循环切换后令牌还原、且旧方案自带浅色文字令牌。

### V-05 ttk Treeview 无法逐行绘制横向细线

- **现象**：规格要求「表格只留横向细线」；ttkbootstrap 的 Treeview 布局无 `Treeitem.separator` 元素，逐行细线无元素可依附。
- **根因**：ttk 的 Treeview 不提供行分隔图元；斑马纹又被本体系明确禁用。
- **解决方案**：横向细线 = ①表头纸底与白色主体的明度差 + ②表头底部 1px 细线 + ③外框 1px；行间改用 30px 行高与留白分离。竖线本就不绘制，无需额外去除。

### V-06 测试断言更新记录

- **现象**：既有测试只覆盖功能，不覆盖视觉契约（图标名清单、出墨、配色循环、新样式存在性）。
- **根因**：新视觉体系缺少契约护栏。
- **解决方案**：新增 `VisualContractTests` 5 项：①既有 32 个图标名全保留 + 3 个新增 = 35；②图标出墨回归（V-01）；③配色机制（3 套、默认宣纸·墨黛、循环与令牌还原、旧方案浅色文字令牌、未知方案拒绝）；④纸墨基底令牌值；⑤新样式（`BandTitle/BandSub/Ghost.TButton`）存在且表格行高 30、输入框凹陷底。既有断言无需修改，全部保留并通过。

## 三、视觉重构 · app.py 版式落地（V-07 ~ V-10）

> 功能、事件绑定、业务方法零变更（AST 核对见变更-11）。

### V-07 参数配置页三块面板被拉高、出现大片空白

- **现象**：设置页三个面板在滚动画布内各占约 1/3 视高，「纸墨配色」面板正文区出现约 150px 空白，「当前配色方案」提示行也因初始文本为空而不可见。
- **根因**：`_panel()` 固定 `expand=True`；页面内容总高小于画布视高时，pack 会把余量按比例分给三个面板，使面板被拉高。`_palette_hint` 建项时 `text=""`，只在 `_apply_palette()` 里赋值，默认配色启动时永不触发，提示行空白。
- **解决方案**：`_panel()` 增加 `expand=True` 形参；任务布设页与参数配置页（滚动页）三块面板改传 `expand=False`，让面板按内容高度排布、由画布承担滚动；`_palette_hint` 建项即写入 `当前配色方案：{theme.CURRENT_PALETTE}`。

### V-08 配色切换后面板标题带、芯片、菜单残留旧配色

- **现象**：`_repaint_*` 原只重绘导航栏、按钮图标与表格标签；切到「黛蓝·琥珀」后，面板标题带纸底、标题带图标、统计芯片底/数值色、下拉菜单底色仍停留在旧配色。
- **根因**：这些元素是 tk 原生 widget，不走 ttk 命名样式，`apply_theme()` 刷不到；原实现也没有登记它们。
- **解决方案**：新增登记表——`_surface_slots`、`_fg_slots`、`_panel_slots`、`_menus` 四类，配套 `_reg_surface()` / `_reg_fg()` 登记入口；`_apply_palette()` 依次调用 `_repaint_surfaces()` / `_repaint_panels()` / `_repaint_menus()` 重绘。导航激活项图标抽出 `_paint_nav_item(key, active)` 按当前底色重绘。全部为重绘，无控件增删。

### V-09 测试断言核对结论（无冲突）

- **现象**：规格要求「若新版式与结构断言冲突，只更新结构断言本身」。
- **根因**：不适用——结构断言的四页键、导航项、tree、result_text、各方法全部原样保留；视觉契约断言与版式无关。
- **解决方案**：未修改任何测试断言，全部通过，无回归。

### V-10 可视化探针自身 PNG 写出缺陷

- **现象**：探针初版 `chunk()` 把 4 字节长度也计入 CRC，导致产物 PIL 无法识别（截图全部无法解码）。
- **根因**：PNG 规范的 CRC 只覆盖「类型 + 数据」两段，不含 4 字节长度字段；手写编码器多算了一段。
- **解决方案**：改为对 `tag + data` 计算 CRC 后再拼长度，截图全部可正常解码。

## 五、安全加固轮（S-01 ~ S-12）

> 范围：安全审查发现 F-01 ~ F-12、D-01 的全部处置，详见 `04-安全设计说明.md` §9。

### S-01 导出 CSV 公式注入（F-01）

- **现象**：导出含 `=HYPERLINK(...)` 与 `+cmd|'/c calc'!A1` 的链接记录，CSV 原文原样落盘；Excel/WPS 打开即把单元格当公式执行。
- **根因**：`csv.writer` 只做引号/逗号/换行转义，不中和公式语义；链接字段来自不可信第三方页面。
- **解决方案**：`crawler.py` 新增模块级 `_csv_cell()`——以 `=` `+` `-` `@` 或制表/回车开头的单元格加单引号前缀；`_export_csv` 五个文本列全部过闸。

### S-02 私有网段覆盖不全（F-02）

- **现象**：`is_private_host("100.64.0.1")` 返回 `False`；`::ffff:127.0.0.1` 形式的 IPv4-mapped 地址同样漏判。
- **根因**：CGNAT `100.64.0.0/10`（RFC 6598）不在 Python `ipaddress.is_private` 的私有段常量内；映射地址按 IPv6 判定时不看向内层 IPv4。
- **解决方案**：`security.py` 显式拦截 `_CGNAT_NET`；`is_private_host` 对 IPv4-mapped IPv6 先取 `ipv4_mapped` 再判定。

### S-03 域名解析失败即放行（F-03）

- **现象**：`resolved_is_private("no-such-host.invalid")` 返回 `False`（DNS 故障被当作公网放行）；`2130706433`（十进制 IP）同样漏判。
- **根因**：旧实现把「解析失败」与「解析为公网」混为一个返回值，调用方无法区分，等于把 DNS 故障变成 SSRF 窗口。
- **解决方案**：`resolved_is_private` 三态化（True/False/None）；`_host_is_blocked_private()` 统一判定——字面 IP 直接判，域名解析一次并按 host 缓存，None 一律按不安全处理。**残余**：校验-连接两次解析的重绑定 TOCTOU 窗口仍在，列为待排期。

### S-04 种子 URL 无私有校验（F-04）

- **现象**：`validate_target("http://127.0.0.1/ok")` 默认放行；种子 URL 与页面链接不过私有地址策略，仅重定向路径有 `block_private_redirects`。
- **根因**：`allow_private=True` 是 `validate_target` 默认值，`_perform` 未传策略。
- **解决方案**：新增 `network_policy.block_private_targets`（默认 True）：`_perform` 对所有抓取目标先过 `validate_target(allow_private=False)`；内网站点用户在 `enhanced_config.json` 置 `false` 放行。

### S-05 排除正则重复编译与爆炸半径（F-06）

- **现象**：每个链接都对同一组模式重新 `re.search` 编译；病态模式的灾难性回溯无语言级超时。
- **根因**：`excluded()` 内联 `re.search(pat, link)`，无编译缓存。
- **解决方案**：`_compiled_exclude()` 按 pattern 缓存编译结果（失败缓存 None），保留 512 上限与 `re.error` 容错。**残余**：无超时机制，建议后续引 `re2`。

### S-06 ftp/sftp 虚假体检结论（F-07）

- **现象**：`check_links(["ftp://a.com/x"])` 返回 `('ok', None)`——零请求即判定可用。
- **根因**：ftp/sftp 无 HTTP 语义、不走 `_perform`，旧代码为「避免报错」直接置 ok，构成虚假结论。
- **解决方案**：改判 `('error', 'ftp/sftp 协议不支持自动体检')`，原因随结果入库，界面与导出口径一致。

### S-07 GUI 事件泵单事件异常放大（F-08）

- **现象**：`_poll_events` 只捕获 `queue.Empty`；任一 `_handle_event` 抛错会丢弃本 tick 剩余事件，异常冒泡到 Tk 回调，且 60ms 续跳被打断。
- **根因**：异常隔离粒度在「整轮排空」而非「单事件」。
- **解决方案**：`_handle_event` 调用包单事件 try/except，`log.exception` 留痕后继续排空。

### S-08 robots 放行无留痕（F-09）/ is_valid_url 职责含混（F-10）

- **现象**：robots 读取/判定异常一律放行但只记 debug 日志，线上排障时不可见；`is_valid_url` 的凭据校验因 `normalize_url` 先行剥离凭据而成为死代码，且对私有地址返回 True，与引擎策略表意不一。
- **根因**：前者日志级别选择低估了排障需求；后者函数承担了「语法校验」与「策略判定」双重语义。
- **解决方案**：robots 两处异常日志升为 warning（fail-open 行为不变）；`is_valid_url` 文档字符串明确职责边界，并用测试钉住分层。

### S-09 图标缓存跨 Tk 根失效（F-12）

- **现象**：同进程构建第二个 Tk 根并 `App(root)` 时报 `image "pyimageNN" doesn't exist`。
- **根因**：`icons.icon()` 的全局缓存未按 Tk 根分区，第二个根复用了第一个根已消亡的 PhotoImage。
- **解决方案**：缓存键纳入当前默认根对象（强引用防 id 复用误命中），按根分区；单根产品行为不变。

### S-10 依赖环境漂移（D-01）

- **现象**：`requirements.txt` 锁 `urllib3==2.8.0`，运行环境实装 2.7.0，`pip-audit` 对实装版本报 3 项已公开漏洞，而按清单扫描却显示 0 漏洞——锁定清单与实际环境不一致。
- **根因**：环境安装滞后于清单锁定；此前轮次只按清单扫描，未核对实装版本。
- **解决方案**：运行环境升级 `urllib3==2.8.0` 并复验 requests 兼容；`pip-audit`（清单）与环境扫描双双 0 漏洞。

### S-11 测试套件 Windows 致命崩溃（F-13）

- **现象**：全量门禁约每 3 次运行出现一次 `Windows fatal exception: code 0x80000003` 致命崩溃，进程整体死亡；崩溃点随运行漂移——出现过 socketserver 线程与 ThreadPoolExecutor 工作线程的 GC 竞争。
- **根因**：CPython 的 cyclic GC 可在任意线程发起；测试进程内同时存在 Tk 对象（PhotoImage 的 `__del__` 会调用 Tcl）与网络工作线程。GC 在非主线程回收 Tk 对象不满足 Tcl 线程模型，触发致命异常。
- **解决方案**：
  1. **测试侧**：新增 `conftest.py`，会话导入即 `gc.disable()`——引用计数回收确定性，全部用例显式清理，禁用不影响任何用例判定与覆盖。实证：禁用后连续 7 次全量复跑全绿零崩溃。
  2. **产品侧对称防护**：`icons.py` 新增 `_ALL_IMAGES` 强引用注册表，`photo()` 产出的每个 PhotoImage 一律登记，杜绝生产进程中「工作线程 GC 回收 Tk 对象」的同类路径。
  3. **测试服务关闭加固**：测试靶机增加 `block_on_close=False`、`_closing` 标志与 teardown GC 暂停，收窄 socketserver 关闭竞态。
- **结论**：崩溃属「CPython GC × 线程 × Tk 对象」环境级问题，非业务逻辑缺陷；三重处置后该类路径均被确定性封堵。

### S-12 依赖漏洞情报库刷新后的 soupsieve 升级（D-03）

- **现象**：安全加固轮完成后，`pip-audit` 复扫发现 soupsieve 2.9.2 新公开 2 项漏洞（CVE-2026-126190 修复版本 4.0.0、CVE-2026-126192 修复版本 2.10.0）。此前审计快照时该库报 0 漏洞，属漏洞情报库更新后的新发现。
- **根因**：soupsieve 为 beautifulsoup4 的传递依赖，锁定版本 2.9.2 落后于上游修复版本；漏洞情报在审计轮次与复扫轮次之间发布。
- **解决方案**：`requirements.txt` 锁定 `soupsieve==4.0.0`（两项漏洞的最小全解版本），运行环境与测试沙箱同步升级；bs4 4.15.0 对 soupsieve 仅要求 `>=1.2`，选择器冒烟通过，全量测试真实执行通过；复扫 `pip-audit` → No known vulnerabilities found。

### 变更-18 DNS 重绑定 TOCTOU 防护落地（第七轮维护循环，F-03 余项收官）

- **方案**：连接层 IP 钉定——`security.resolve_pinned_ip(host)` 把「DNS 解析 + 私有地址判定」收敛为一次（IP 字面量/代理场景返回 None 走原路；解析失败或私有地址未放行 → fail-closed 抛 `UnsafeUrlError`），连接类 `_PinnedHTTPSConnection` / `_PinnedHTTPConnection` 以该 IP 建 socket，`server_hostname` 保留原域名（urllib3 2.8 `HTTPSConnection` 显式支持），SNI/证书校验语义与直连域名完全一致；`_PinnedAdapter` 覆盖直连池与代理池（教训同 `_SSLAdapter`）。
- **实施缺陷与修正**：初版把 `pin_resolver` 作为池构造 kwarg 传入，实测全部请求 TypeError——urllib3 2.8 的 PoolKey 把 connection_pool_kw 所有字段纳入池键（`key_pin_resolver` 不被 `PoolKey` 接受）。改为包裹池管理器 `connection_from_host`：池首次创建后把 resolver 注入 `pool.conn_kw`，连接类在 `_new_conn` 时读取；不触碰池键。
- **验证**：全量 40 项测试通过（新增 `tests/test_pinning.py`：resolver 单测 4 组、钉定适配器挂载、以 `localhost` 端到端抓取 fixture 证明 socket 钉定路径真实可用、NXDOMAIN fail-closed → error → 退出码 1）；真站冒烟两步——代理模式确认 resolver 收到代理地址（边界成立），`trust_env=False` 直连模式 resolver 返回 `www.itmsky.com → 8.146.211.19`、socket 连 IP、证书校验域名 → 200。
- **边界如实记录**：经代理（含系统环境代理）访问时 DNS 由代理解析，钉定不适用；引擎默认不主动配置代理（用户显式开启时适用）。文档同步：docs/04 §10、docs/06 §10、CHANGELOG v0.4.0。
